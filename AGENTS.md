# EyeTracking practice — development rules

- Product authority: docs/design/EyeTracking-Product-Design-FA-v1.1.pdf (Persian design, v1.1). Build plan and open decisions are on its pages 6–7; the reviewer's nine comments and how each was applied are on page 8. Current state: docs/current-state.md (keep under 5 KB). One short snapshot per build step in docs/features/; overwrite, never append run history.
- Product language: English, left-to-right, for both apps and all participant-facing content. Repository docs may be Persian.
- Stack (from the design): Flutter for the Participant App and the Research Admin panel with a small shared package; Python 3.11 / FastAPI service for accounts, sessions and data; gaze model as a separate worker; SQL database (SQLite for local development and tests, PostgreSQL-ready through SQLAlchemy). Do not replace Flutter with a web framework.
- Clean backend: `eyetracking/domain` is framework-free (dataclasses, rules, errors); `application` owns use cases, ports and authorization policy; `infrastructure` implements SQL, hashing and tokens; `web` is FastAPI composition and HTTP only. No SQL or HTTP in domain/application.
- Clean frontend: features/<name>/domain -> application; data implements repositories; presentation consumes repository ports. No HTTP in widgets.
- Access control is enforced on the server for every request: participants see only their own data; researchers and analysts see only coded data of studies they belong to; admins manage users, studies and members but read study data only as explicit members; the identity-to-research-code link needs the separate `can_link_identity` grant, even for admins. Login email never appears in coded views or exports.
- Consent: an information sheet must have all three mandatory sections (aims, potential sources of discomfort, potential benefits) plus data handling and stop/restart rules before it can be published. A participant is "ready" only with an active consent for the current sheet version and complete demographics.
- Measurement (step 2, `backend/eyetracking/domain/measurement.py`): a session is created only for a ready participant; recording needs a running segment, a stimulus layout and a valid calibration; camera, orientation or zoom changes invalidate the calibration; eye-region results exist only with a passed regional validation on a non-synthetic estimator, otherwise the panel says "not evaluable" and reports face-region attention only; missing data is never "not looking". Validation thresholds live in per-study measurement settings (placeholders 80 % correct, 20 % uncertain, eye region ≥ 2× residual error) until the research team fixes them.
- Practice (step 3, `backend/eyetracking/domain/practice.py`): sessions run one published, immutable protocol version; gradual stages never go back in face level or number zone, change one factor at a time unless the protocol allows both, and never pass `final_zone_limit` (default `near_eyes`; `eye_region` only by explicit reviewer decision); nothing advances on a wrong answer, discomfort or invalid data; "improvement" is reported only when eye share rose, comfort did not worsen and content responses held. Content media is private and served only through signed, expiring links.
- Gaze estimator (`backend/eyetracking/gaze`): swappable behind `GazeEstimator`; the synthetic estimator and an L2CS network without published weights report `synthetic: true`, and sessions recorded with them never yield measurement claims. Frames are processed in memory and never written to disk. Weight files are not committed.
- Tests: `cd backend && python -m pytest -q` (torch tests skip when torch is absent; `pip install -e ".[l2cs]"` for the L2CS adapter); Flutter: `flutter analyze` and `flutter test` in each app. Write logs outside the repository (scratchpad or D:\Work\eyetracking-logs) and record only short summaries in docs.
- Cost control: use the cheapest capable model for routine edits, scaffolding, formatting and UI tests; reserve stronger reasoning for access control, consent rules, measurement validity, architecture and hard failures. Delegate only concrete independent work; do not duplicate investigations across agents.
- Do not commit credentials, participant data, generated build output, `.env` or SQLite database files.
