# تصمیم پیش از اتصال آواتار جریانی (گام ۷)

گام ۷ با ارائه‌دهندهٔ توسعه ساخته شده است: یک ویدئوی نمونهٔ چهره که تکرار می‌شود، صدای خودِ مرورگر و زیرنویس هر جمله. پاسخ‌ها از Claude یا قواعد نمونه می‌آیند و تبدیل گفتار به متن از یک سرور Whisper محلی یا نمونهٔ توسعه. برای چهره و صدای زنده و واقعی، یک فروشندهٔ آواتار جریانی باید انتخاب شود. سند طراحی این را پس از پایلوت و با برآورد جداگانه گذاشته است.

## آنچه آداپتور باید فراهم کند
درگاه `LiveAvatarProvider` در `backend/eyetracking/application/ports.py`:
- `info()`: نام، پیکربندی‌شده یا نه، و جریانی بودن.
- `client_config(avatar_id, voice_id)`: هر آنچه اپ شرکت‌کننده برای نشان‌دادن چهره و پخش صدا لازم دارد، مانند توکن کوتاه‌عمر جلسه. کلید API هرگز به اپ نمی‌رسد.
- `estimate_cost_per_minute()`: برای سقف هزینهٔ مطالعه.

متن هر جمله را همچنان سرور تعیین می‌کند. آواتار فقط همان را می‌گوید، یعنی حالت «تکرار متن» و نه گفت‌وگوی خودِ فروشنده. این شرط از قواعد محدود به موضوع و جمله‌های جایگزین محافظت می‌کند.

## معیارهای انتخاب
| معیار | چرا مهم است |
|---|---|
| تأخیر از متن تا شروع گفتار | مکث طولانی گفت‌وگو را ناخوشایند می‌کند |
| حالت تکرار متن | تا پاسخ‌ها فقط از قواعد ما بگذرند |
| قاب ثابت چهره یا اطلاع از جای چشم و دهان در هر لحظه | بدون آن، ناحیهٔ چشم برای اندازه‌گیری نگاه معتبر نیست؛ همین مسئلهٔ «چهرهٔ متحرک» در سند طراحی است |
| شرایط داده و محل پردازش | آیا متن یا صدا ذخیره یا برای آموزش استفاده می‌شود؛ محل سرورها |
| هزینه به ازای دقیقه و سقف | با سقف هزینهٔ مطالعه سازگار باشد |
| کیت وب سبک | اپ Flutter وب است و باید در Chrome و Edge روی ویندوز کار کند |
| انتخاب چهره و صدای واقع‌گرا یا بازیگر فیلم‌شده | از تصمیم‌های باز صفحهٔ ۷ سند طراحی |

## پیش از اتصال
1. پایلوت با مسیرهای تدریجی و گفت‌وگوی مبتنی بر علاقه انجام شود، و قواعد گفت‌وگوی زنده (محدودیت نوبت، جمله‌های جایگزین، رفتار در ناراحتی) با تیم پژوهش و خانم دکتر مرور شود.
2. فروشنده، شرایط داده، کلید و سقف هزینه تأیید شود؛ این همان تصمیم «قبل از اتصال پولی» در سند طراحی است.
3. آداپتور با آزمون‌های قرارداد درگاه نوشته شود، و یک جلسهٔ آزمایشی با کارکنان روی PC پایلوت اجرا شود.
