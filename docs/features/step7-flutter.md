# Step 7 - Flutter snapshot (live interactive avatar)

Contract: docs/api/step7-live-avatar.md. Two parts below: Participant (with the shared code in `packages/core`) and Admin.

## Participant

Participant App side of the live avatar, plus the shared code it needs in `packages/core` (the admin part uses the same models). Layering as before (domain -> application -> data -> presentation with repository ports, `ChangeNotifier` controllers, fakes for tests), same theme, English, left-to-right, no new packages. Backend untouched.

### What exists

  - `ProtocolPath.liveConversation` (`live_conversation`), `ProtocolDefinition.live` (starter included), `Assignment.isLive`, `SessionOutcomes.conversation` (null on the other paths).
  - `speech/`: `SpeechSynthesizer` port and `createSpeechSynthesizer()` (conditional import like the other web / stub pairs). Web: `window.speechSynthesis`, picks an English voice (en-US, then en-GB, then any en*; otherwise asks for en-US), cuts off a line still being spoken, never throws. Stub: silent. `AudioRecorder` port, `AudioClip` (bytes, content type, duration, `mediaType`, `filename`), `AudioRecorderException` and `createAudioRecorder({maxDuration})`. Web: `getUserMedia` audio only + `MediaRecorder`, `audio/webm;codecs=opus` when supported, else the browser default; stops by itself after 30 s (`onLimit`, the clip is then returned by `stop`); every track is stopped when a clip ends or is cancelled; letting go or cancelling while the permission prompt is open starts nothing; messages for a blocked, missing or busy microphone. Stub: unsupported (start says to type instead). `FakeSpeechSynthesizer` and `FakeAudioRecorder` (scripted clip, `hitLimit`, start gate and error) are in `testing.dart`.
  - `VideoStageConfig.loop` and `.muted` (web `<video>` loop / muted, so the sample face starts without a tap; the fake never ends a looping video).
- `apps/participant` (`features/session/`):
  - `domain/live_repository.dart` (port), `data/api_live_repository.dart`: `snapshot`, `start`, `sendTurn`, `sendAudio` (multipart: `expect_turn` and `t_ms` fields before the file, media type without parameters), `end`. The avatar's `video_url` (`/static/live/...`) is resolved against the service address.
  - `application/live_practice_controller.dart`: phases loading -> choose -> conversation -> ended -> (finished) and post. Loads where the conversation stands (none: choice card; open: start with `resumed`, not read out again; closed: practice finished at once). Typed turns send `expect_turn = turns_used`; one request in flight at a time; 409 sets `conflict` (Reload reads GET live again and carries on), other failures show the text as written (Try again keeps the typed text). Voice on / off (speaks opening, replies and closing through the core helper). Push to talk with the recorder port, `Type instead` / `Speak instead`. Distress from the last response shows the break offer until dismissed, the next turn or a pause. Maps `face_layout` onto the rectangle the video is drawn in and hands it to the `SegmentRecorder` (opens when the picture is moving, posts again when the rectangle changes, closes at Continue). Post observation with its own clock. Pause, resume, device change and cancel like the interest controller.
  - `SessionFlowController`: `isLive`, `live`; `startPractice` creates the controller (needs the live port and the voice), `startPost` replays the avatar (`practiceVisible` and `_isObservationStep` know the live post), pause / resume / end early / device change / dispose reach the live controller; the protocol's closing line is rendered with the participant's name and topic as a fallback.
  - Presentation: `LivePracticeView` (avatar stage, caption, development badge, turns left, Voice on / off, End conversation, break offer, error with Reload / Try again, input), `LiveChoiceCard`, `LiveTypedInput` (Enter sends, Shift+Enter new line, counter, field off while a turn is in flight, draft kept in the controller), `LiveSpeechInput` and `PushToTalkButton`. Instructions, post panel and introduction mention the chat; the topic screen says the avatar chats and, because the server makes a live assignment `ready` at once, "Your conversation is ready." instead of "Content being prepared".
  - Summary: the conversation card (your messages, on topic share or "Not judged", how it ended, note that the reply model judges it) takes the place of the comprehension card on the live path; the third improvement criterion reads "The conversation held". Fact values now wrap instead of overflowing.
  - `AppDependencies.live`, `.speech`, `.audioRecorder` (a factory, the recorder is made when speech is first needed); `bootstrap.dart` wires `ApiLiveRepository`, the browser voice and the browser recorder.

### Choices
- After the closing line the participant presses Continue (the line can be read and heard; the practice segment stays open until then). The flow then goes on to the post observation as for the other paths.
- The window never scrolls: the video box and the posted face regions stay where they were measured. From 900 px the panel sits right of the video (400 px), below 900 px under it (at most 66 % of the height, scrolling inside; the break offer and an error come first). The input is always visible. With a keyboard at hand (>= 900 px) the text field takes focus on its own.
- Without `face_layout` in the protocol the practice and post segments are not recorded (no region claims are possible); the baseline still is, and the conversation runs. Same rule as an interest segment without a layout.
- When the transcript is not kept the server removes the text of every turn when it closes, also the closing turn in its own response (checked against the real backend). The app then shows the protocol's `closing_line` with name and topic filled in, so what is read and heard is what the server said.
- Push to talk: pressing starts the recording, holding longer than 450 ms and letting go sends it, a short tap leaves it running until the next tap; Enter / Space and screen readers act as a tap. A clip under 300 ms is dropped ("We did not hear anything"). The recording is held in memory until uploaded; the microphone is released after every clip, on pause, on End and on Type instead. A blocked or missing microphone says so and switches to typing.
- The post observation plays the looping avatar again for `post_seconds` (the clock starts when the picture moves, pause holds it), with no caption, no voice and no input.
- Speech is offered on the card whenever the protocol lists it; if the server cannot do speech it answers 409 ("please choose typing") and the message is shown on the card.
- The participant's own line is echoed under the avatar's caption ("You: ..."): for a spoken turn that is what the server understood, so it can be checked.

### Run (backend :8000)
- `cd apps/participant && flutter run -d chrome --web-port=8080 --dart-define=API_BASE_URL=http://localhost:8000`. `python scripts/seed_demo.py ...` (or `scripts/run-local.cmd`) assigns the demo live protocol; confirm the topic on the home screen, then "Prepare for session". The development providers answer without keys; the fake speech provider "hears" a fixed sentence.
- Tests: `flutter analyze` and `flutter test` in `packages/core` and `apps/participant`; `flutter build web --release --no-web-resources-cdn` in `apps/participant` (delete `build/`).

### Missing
- Not seen in a real browser: the web `speechSynthesis` voice, the microphone permission prompt and `MediaRecorder` (only compiled and exercised through fakes), and the real `<video>` loop with the gaze layout. The step 6 e2e route would apply (docs/features/step6-e2e.md); a headless browser has no microphone, so speech needs a manual try.
- Earlier turns of a long conversation are not shown (only the current avatar line and the participant's last line); there is no full transcript view.
- A closed conversation found when the practice starts (a session resumed after a reload; the app does not resume sessions today) skips the post observation's avatar, because the avatar settings only come with the start response.
- The `time_limit` is enforced by the server on the next turn; the app shows no countdown.
- `captions` from the avatar settings is not used (the caption is always shown).
- Streaming avatars: the app plays the sample video and the browser voice only (as the contract says for development).
- Seen in a headless browser (docs/features/step7-e2e.md): typed conversation, distress banner, closing, post segment and summary. After review, "Keep talking" and dismissing an error give the keyboard back to the message box, and the server now returns the closing line also when no transcript is kept, so the app's local fallback is rarely used.

## Admin

Research Admin side of the live avatar. Contract: docs/api/step7-live-avatar.md. Layering as before (domain -> application -> data -> presentation, `ChangeNotifier` controllers, ports faked in `test/fakes.dart`), same theme, no new packages. Backend, `packages/core` and `apps/participant` untouched by this part.

### What exists
- Models: the shared ones from `packages/core/lib/src/models/live.dart` (protocol `LiveProtocolConfig` on `ProtocolDefinition.live`, `LiveConversation`, `LiveTurn`, `ConversationOutcome`, `LiveEndReason`) plus staff-only models owned by the admin app in `features/live/domain/live_models.dart`: `LiveAvatarStatus` (+ `LiveProviderInfo`), `StaffConversation`, `ConversationMonitor` (+ `MonitorLastTurn`), `ConversationReportColumns`, and the staff wording (`conversationEndReasonLabel`, `conversationFlagLabel`, input mode).
- `features/live/`: `LiveRepository` port (`status`, `conversation`; 404 of the conversation is `null`) and `ApiLiveRepository`; `LiveAvatarController` (a 404 of the status hides the card: an older service), `SessionConversationController`; presentation `LiveAvatarCard`, `SessionConversationSection`, `FlagChips`, `FaceLayoutPreview`.
- Protocol editor (`features/protocols/`): path `Live conversation with an avatar` is chosen like the other two; `LiveSettingsSection` with the four limits, the four scripted lines (multi-line, counter, hint that {{display_name}} and {{topic}} are filled in and links/e-mail are not allowed), avatar and voice ids (hint: future streaming vendor), input modes Typed / Speech (at least one), the transcript switch, and an optional face layout (switch, twelve fractions, preview of the three boxes, the rule that the eye region lies above the mouth region). `LiveSettingsDraft` keeps the text and mirrors the server's ranges and text rules per field (`liveErrors`); Save is refused with the first message, the server's 422 text is shown as written. Published versions are read-only; analysts read. The shared field widgets moved to `editor_widgets.dart` (`EditorText` gained multi-line, error and counter).
- AI tab: "Live avatar" card (reply, speech, avatar provider with model, effort, local speech address, Configured / Not configured, the existing "Development provider" badge for synthetic, "No streaming avatar connected" when `streaming` is false, per-reply and per-minute estimates, shared budget, open conversations, the server note). Read again by Refresh, when the tab comes back into view and after a new cost cap is saved. Server refusals shown as written with Try again. `LabelRow` and `FigureText` moved to `ai_widgets.dart` for both cards.
- Session detail: "Conversation" section after the protocol (topic, input mode, transcript kept, status, end reason, turns used, cost; outcome with participant turns, on-topic share and the note that the reply model judges it, redirects, distress; turn list with role, session time, flags as chips, text or "Text not kept"; one-line note that opening it is logged). 404 shows nothing, other failures show the server text with Try again. For the live path the third improvement criterion reads "Conversation held (judged by the reply model)".
- Pilot tab: the Live monitor panel shows the `conversation` block (status, input mode, turns used, distress highlighted above 0, redirects, last turn role and flags, end reason); the Report rows table has Conversation turns, On-topic share, Conversation distress, Conversation end (dashes when null).
- Ports: `PilotRepository.live` now returns `LiveReading` (core `LiveStatus` + `ConversationMonitor?`) and `report` returns `PilotReportData` (core `PilotReport` + conversation columns by session id), because the shared pilot models do not carry the new fields. `AppDependencies.live` is new.
- AI text-job form: assignments of the live path are not offered (nothing to generate; the confirmed topic is all the avatar may talk about).

### Choices
- Roles follow the existing rule (`canEdit` is everyone except analysts). Analysts read the live settings, the card, the conversation and the report; the server refuses them the monitor and every write.
- The live section checks ranges and text rules per field before sending (same wording as the server's rules); the server still decides and its 422 text is never rewritten.
- The face layout is optional: off sends no `face_layout`. Switching it on starts from a sample (face 0.3 0.1 0.4 0.8, eyes 0.3 0.25 0.4 0.2, mouth 0.35 0.55 0.3 0.2); the preview leaves out a box that is not complete and draws both regions red when the eye region is not above the mouth region.
- The conversation read is logged by the server on every 200 (`live_transcript`), so the section says so; a session without a conversation (404) is never logged.
